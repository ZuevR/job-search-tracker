# Задача 4 — загрузка данных в Server Components: последовательно и параллельно

**Статус:** ✅ закрыта 20.11.2026 (выдана 18.11.2026)
**Модуль:** 2 — Данные (пункт плана 4, часть 1; `searchParams` будут в задаче 5)

## Условие

**Зачем:** в App Router данные загружают прямо в серверном компоненте через `await fetch(...)`, без `useEffect`, `useState` и своего API-слоя. Ключ к агрегатору остаётся на сервере, а в браузер уходит готовый результат. Главная ловушка — **водопад**: несколько `await` подряд выполняются последовательно, даже если запросы друг от друга не зависят. «Как убрать водопад» — один из самых частых вопросов по RSC. Плюс особенность Next 16 с Cache Components: незакэшированные данные нужно явно обернуть в `<Suspense>`, иначе сборка подскажет ошибкой.

**Прочитать:**
- https://nextjs.org/docs/app/getting-started/fetching-data — разделы «Server Components → With the fetch API», «Examples → Sequential data fetching» и «Parallel data fetching». Локально: `node_modules/next/dist/docs/01-app/01-getting-started/06-fetching-data.md`.
- https://nextjs.org/docs/app/getting-started/caching — только раздел «Streaming uncached data». Остальное будет в задачах 6–7.
- https://react.dev/reference/react/Suspense — раздел «Usage → Displaying a fallback while content is loading».
- `aggregator/README.md` — контракт агрегатора: эндпоинты, задержки, типы ответов.

**Сделать:**
1. **Запусти агрегатор.** `cp .env.example .env.local`, затем `yarn aggregator` в отдельном терминале (вместе с `yarn dev`). Проверь в браузере `http://localhost:4000/api/stats`.
2. **Клиент агрегатора** — `lib/aggregator.ts`: типы из README и функции `getStats()`, `getVacancies({ limit })`, `getVacancy(id)`, `getCompany(id)`. Базовый URL берётся из `process.env.AGGREGATOR_URL`. Если ответ не `ok`, функция бросает ошибку.
3. **Страница «Обзор»** (`/dashboard`), три блока:
   - статистика: всего вакансий, удалённых, новых за 24 часа, средняя зарплата «от» (`Card`);
   - «Свежие вакансии»: 5 последних (название, компания, город, зарплата);
   - «Вакансия дня»: `v-001`, и рядом её компания (название, рейтинг) через `getCompany(vacancy.companyId)`.
4. **Версия 1, «в лоб»:** все четыре запроса через `await` подряд. Сделай полную перезагрузку (`Cmd+R`) и по логам агрегатора посчитай общее время от первого `→` до последнего `←`.
5. **Версия 2, параллельно:** перестрой загрузку так, чтобы общее время стало минимально возможным. **До замера посчитай**, каким оно должно получиться при задержках из README и почему не меньше.
6. **Сборка.** Запусти `yarn build`, прочитай ошибку или подсказку Next и исправь её минимально: заголовок страницы остаётся вне `<Suspense>`, блоки с данными — внутри, fallback простой текст. Посмотри, каким значком теперь помечен `/dashboard` в таблице маршрутов.
7. **Прод.** Задеплой агрегатор отдельным проектом Vercel по README (раздел «Деплой на Vercel») и пропиши `AGGREGATOR_URL` в проекте Next. Только после этого пушь.

**Готово, когда:**
- `/dashboard` показывает все три блока с реальными данными агрегатора, и в прод тоже.
- В «Результате» таблица: версия → время по логам агрегатора (от первого `→` до последнего `←`) → твой прогноз. Для версии 2 одной фразой объяснено, почему время именно такое.
- Данные грузятся только на сервере: `'use client'` для них нет, `AGGREGATOR_URL` без `NEXT_PUBLIC_`.
- `yarn build` проходит. В «Результате» одной фразой: каким стал значок `/dashboard` и что это значит по сравнению с `○`.
- `yarn lint` чистый.

**Подсказки:** только по запросу.

## Результат

**Клиент агрегатора** (`lib/aggregator.ts`): приватный generic-хелпер `request<T>(path)` (проверка env, `res.ok`, ошибка `[GET path] Response status: N`), четыре однострочные функции. Query через `URLSearchParams` без `?` при пустых параметрах, `id` через `encodeURIComponent` (без него `a?fail=1` давал 500 — инъекция служебного параметра; с ним 404).

| Версия | Время по логам агрегатора (первая `→` … последняя `←`) | Прогноз |
|---|---|---|
| 1. `await` подряд | 3052 мс (19:48:04.428 → 19:48:07.480) | не делал |
| 2. параллельно (`Promise.allSettled` + цепочка vacancy→company одним промисом) | 1318 мс (20:52:27.040 → 20:52:28.358) | 1300 мс: компания ждёт вакансию (500 + 800), это самая длинная цепочка |
| 3. `<Suspense>` на блок, каждый блок грузит свои данные | 1311 мс (23:14:16.565 → 23:14:17.876) | — |

`yarn build`: `/dashboard` → `◐` (Partial Prerender): при сборке готовится статическая оболочка (layout, навигация, `<h1>`, fallback-и `<Suspense>`), а блоки с некэшированными данными рендерятся на запрос и стримятся в тот же ответ; у `○` весь HTML готов при сборке, и на запрос сервер ничего не рендерит.

## Ревью

**Что хорошо**
- Клиент агрегатора собран чисто: один generic-хелпер, ошибки с путём и статусом, query без мусора, безопасные `id`. Эти сообщения потом нашли причину падения прода за минуту.
- Прогноз версии 2 точный (1300 → 1318 мс), с правильной причиной: критический путь vacancy → company.
- Сам пошёл дальше задания: частичная деградация через `allSettled`, логирование там, где ошибку гасят.
- Форматирование вынесено из `utils.ts` в отдельный модуль, клиентский граф `cn` остался чистым.
- `satisfies` + `keyof typeof LABELS`: TS снова проверяет код, а не верит на слово.

**Что повторялось**
- 🔴 Висящий промис: `getStats()` и `getVacancies({})` без `await` — дважды. Правило: каждый промис либо `await`, либо явно передан дальше.
- 🟡 Приведения типов, которые отключают проверку: `as [keyof Stats, number][]`, `as [keyof Stats, string][]`.
- 🟡 Проверка результата: замер версии 1 и лог `a?fail=1` — только после напоминания; `getVacancies` с неиспользованным `urlParams` — сам по логу не заметил.
- 🔵 Ответы «по факту» без механизма («потому что серверная», «каждый в своём темпе»). После разбора — с механизмом.

**Инциденты при деплое**
- Агрегатор: yarn 4 в подпапке поднимался до корневого проекта → собственный `aggregator/yarn.lock` (чинил Claude).
- Прод Next: `AGGREGATOR_URL` без `/api` → 404 на всех блоках, вся страница — заглушка ошибки (нет `error.tsx`). Причина найдена по `digest` в Runtime Logs Vercel, исправлено значение + Redeploy.
- Эксперимент: сборка без `AGGREGATOR_URL` падает на пререндере `/dashboard` (проверка env стоит до `fetch`) → Vercel не публикует сломанный деплой.

**Решение:** задача закрыта. Код в `main` (`396ddf7`), прод проверен: три блока с данными, запросов к агрегатору из браузера нет.

## Вопросы на понимание

**Почему без `await` был `unhandledRejection`, а страница не упала?**
Ответ Ромы: попросил объяснить.
Разбор: async-функция сразу возвращает промис; ошибка внутри неё переводит промис в rejected, а не бросается в момент вызова. Компонент не ждал промис и успешно отрендерился, React о нём не знал. Реджект без обработчика ловит Node как `unhandledRejection`. С `await` реджект становится `throw` внутри рендера, и его обрабатывает React/Next (оверлей в dev, `error.tsx` в проде). Линт-правило: `@typescript-eslint/no-floating-promises`.

**Аннотация `Promise<Stats>` проверяет данные в рантайме? Что будет, если агрегатор переименует поле?**
Ответ Ромы: нет; упадёт приложение. 🟡
Дополнение: не обязательно упадёт. `undefined` в JSX даст пустоту, в арифметике — `NaN`: тихо неверные данные хуже падения. Падение (`TypeError` в компоненте) — далеко от причины. Внешние данные валидируют на границе (zod `parse` в клиенте), тогда ошибка возникает в момент получения с понятным сообщением.

**Зачем `encodeURIComponent` для `id`?**
Ответ Ромы: без кодирования `a?fail=1` давал 500, с кодированием 404. ✅
Дополнение: `?` начинает query, поэтому пользователь подставил служебный параметр в запрос к чужому API (так же `delay=30000`). С кодированием `?`→`%3F`, всё остаётся одним сегментом пути. То же с `/` (`../stats` → `..%2Fstats`).

**Попадёт ли код серверной карточки в клиентский бандл?**
Ответ Ромы: в бандл попадают модули с `'use client'` и всё, что они импортируют (не через `children`); на пути к `StatsCard` нет `'use client'`. ✅ (со второй попытки)
Дополнение: решает граф импортов, а не место вызова. `formatSalary` в `utils.ts` оказался бы в клиентском графе, потому что `utils` импортирует `nav-link.tsx` ради `cn`. Type-only импорты — через `import type`, чтобы гарантированно стирались.

**`Promise.allSettled` vs `Promise.all`?**
Ответ Ромы: `allSettled` даёт результат по каждому промису; при `all` упал один — упали все. ✅
Дополнение: при `all` `await` бросает, и падает рендер всей страницы (оверлей / `error.tsx`). `all` не отменяет остальные запросы — они дойдут до агрегатора. Ловушка: `allSettled` ловит и служебные ошибки Next (сигналы пререндера, `notFound`, `redirect`) — для них `unstable_rethrow`, а идиоматичный путь — error boundary.

**Почему без `Promise.all` запросы в версии 3 стартовали в одну миллисекунду?**
Ответ Ромы: запросы в разных компонентах, как async-функции в синхронном коде — ожидание только внутри функции. 🟡
Дополнение: React вызывает компонент, получает промис и не ждёт его на месте: отмечает поддерево приостановленным, показывает fallback ближайшего `<Suspense>` и рендерит соседей. За один проход стартуют все `fetch`; по готовности поддерево дорендеривается и досылается в поток. Водопад — это `await` подряд в одном компоненте.

**Что значит `◐` в сравнении с `○`?**
Ответ Ромы: комбинация пререндера и стриминга; динамическая часть приходит RSC payload внутрь статического роута. 🟡
Дополнение: при сборке готова статическая оболочка (layout, навигация, `<h1>`, fallback-и). Динамическую часть задают границы `<Suspense>` вокруг некэшированных данных. При первой загрузке она дописывается в тот же HTTP-ответ кусками HTML со скриптом подмены; RSC payload — при клиентской навигации.

**Почему данные «Обзора» не грузят в `dashboard/layout.tsx`?**
Ответ Ромы: layout не перерисовывается при навигации внутри `/dashboard/*`, меняется `children`; layout не может передать данные в `page`. ✅
Дополнение — следствия: данные устаревают при навигации туда-обратно; первая загрузка любой `/dashboard/*` ждёт ненужные запросы; `page` всё равно запросит их сам (дубли → `React.cache` / `'use cache'`, задача 6).

**Что сделал бы Next с `NEXT_PUBLIC_AGGREGATOR_URL`?**
Ответ Ромы: подставил бы значение в клиентский бандл при сборке; изменение на хостинге без пересборки не сработает; значение видно любому пользователю. ✅
Дополнение: серверная переменная читается в рантайме — на своём сервере достаточно рестарта процесса, один образ можно запускать в staging и prod с разными env. На Vercel деплой — неизменяемый снимок env, поэтому Redeploy нужен в обоих случаях, но `NEXT_PUBLIC_` требует именно пересборки.

**Один `<Suspense>` на три блока вместо трёх?**
Ответ Ромы: блоки появятся одновременно, когда отработают все три запроса; нужно, если важно «всё или ничего». ✅
Дополнение: появятся через ~1,3 с (по самому медленному). Плюс — один сдвиг вёрстки вместо трёх и согласованный вид. Компромисс между скоростью первого контента и стабильностью раскладки.
