## Что понял

- Типы маршрутов (`LayoutProps`, `PageProps`) — глобальные, их генерирует Next в `.next/types` по структуре `app/`.
- Layout не перерисовывается при навигации внутри своего сегмента.
- С `cacheComponents` ушедшие маршруты прячутся через `<Activity>` (до 3 штук), а не размонтируются: сохраняются state и DOM.
- `metadata` сливается по дереву сегментов; `title.template`/`default`/`absolute`.
- `next/font`: шрифт скачивается при сборке и раздаётся со своего домена; fallback с подогнанными метриками против CLS; `variable` только объявляет CSS-переменную.
- Cascade layers: стили вне `@layer` побеждают утилиты Tailwind 4.
- `'use client'` помечает границу модуля в графе импортов, а не «интерактивность». Client Components рендерятся и на сервере (SSR), и в браузере.
- Серверный компонент, импортированный в клиентский файл, становится клиентским; переданный через `children` — остаётся серверным (interleaving).
- При клиентской навигации сервер отдаёт только RSC payload меняющегося сегмента, HTML не нужен.
- Props Server → Client сериализуются: функции нельзя (кроме Server Actions).
- shadcn — исходники в проекте, а не пакет; `cn` = clsx + tailwind-merge (разрешает конфликты классов).
- Водопад: `await` подряд в одном компоненте. Время = критический путь (самая длинная цепочка зависимых запросов): 3052 → 1318 мс.
- Ошибка async-функции живёт в её промисе; без `await` React о ней не узнает (`unhandledRejection`).
- `fetch` реджектит только на сетевых ошибках, 4xx/5xx — проверять `res.ok`. Аннотация типа не валидирует данные.
- `encodeURIComponent` для всего внешнего в URL: иначе `?`, `/`, `#` меняют структуру запроса.
- В бандл попадает то, до чего дотягиваются импорты из `'use client'`, а не то, что вызывают. Типы — `import type`.
- `<Suspense>` ловит ожидание только потомков → `await` переносят в компоненты блоков; соседние async-компоненты грузятся параллельно без `Promise.all`.
- `◐`: статическая оболочка при сборке + блоки в `<Suspense>` стримятся в тот же ответ.
- Next использует исключения для управления потоком (пререндер, `notFound`, `redirect`) — общий `catch` их гасит.
- В проде текст серверной ошибки скрыт, связь с логами — `digest`. Проверка env до `fetch` роняет сборку → сломанный деплой не публикуется.

## Слабые места

- Проверка результата: «Готово, когда» — проверять самому (деплои в Vercel, lint). → в задаче 4: лог агрегатора смотреть самому после каждого изменения.
- ❗ Static vs dynamic: путает «где рендерится» и «когда». Клиентский JS не делает страницу динамической; динамической её делают данные запроса (`cookies`, `headers`, `searchParams`, некэшированные данные). → в задаче 3 подтверждено: с клиентскими `NavLink` и `DropdownMenu` все маршруты `○`. Добить в модуле 6.
- ❗ «Сохранение при навигации» объяснял через `'use client'`. На деле дело в том, какой сегмент перемонтируется: общий layout остаётся, `page` меняется. → ✅ задача 3, эксперимент б).
- RSC payload: ожидал увидеть в нём HTML. → ✅ задача 3: payload — результат рендера серверных компонентов со ссылками на клиентские модули.
- Root layout = HTML-документ (вместо `index.html`/`_document`), `<head>` собирается из Metadata API.
- Токены shadcn выбирает по названию, а не по смыслу (`accent` ≠ бренд, `chart-*`/`ring` не для UI). → следить в каждой UI-задаче.
- Копипаст без чтения (иконка `Badge` вместо компонента, мёртвые классы). → каждый класс должен уметь объяснить.
- Объяснения «по факту» без механизма (`children`, `key`). На собеседовании отвечать: что происходит → почему. → в задаче 4 снова («потому что серверная», «каждый в своём темпе»), после разбора — с механизмом.
- ❗ Висящие промисы: дважды вызов async-функции без `await` (задача 4).
- Приведения типов `as`, которые выключают проверку TS. Сначала искать способ, при котором TS выводит тип сам (`satisfies`, `keyof typeof`).
